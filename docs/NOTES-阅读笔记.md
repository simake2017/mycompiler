## 一、Lexer —— 游标与 peek 的语义

**出处**：`src/lexer.cpp:122,149,275,302,303,442`

| 笔记 | 说明 |
|---|---|
| `m_source(std::move(source))` —— "这里会设置相应的值" | 构造函数把源串搬进成员，`m_pos` 从 0 开始 |
| `m_source[m_pos++]` —— "指针会移动" | `advance()` 是**取当前字符并前进一步**，返回的是旧值 |
| `peek()` —— "peek 指针不会移动" | 只读不推进。凡是需要"看一眼再决定"的地方都用它 |

★ **这两者的分工是词法分析器里最容易写错的地方**：

```text
advance()  →  返回 m_source[m_pos]，然后 m_pos++
peek()     →  返回 m_source[m_pos]，m_pos 不动
```

scanIdentifier 里 `text += advance();` 的循环条件用的是 `peek()` —— 只有
"确认下一个字符仍是标识符字符"才推进，这是典型的 peek-then-advance 结构。

| 笔记 | 说明 |
|---|---|
| "每个标识符或者关键字都是用字母或者下划线开头" | 首字符判定比后续字符严：首字符不能是数字 |
| "这里是读取到内容是 `\`（反斜线）的意思" | 行拼接（line splicing）：`\` + 换行 = 逻辑上同一行 |
| "这里只是往前推进，但是不添加到 text 当中" | 反斜杠本身**不进入** token 文本，只消费掉 |

## 二、Preprocessor —— 条件编译的状态机

**出处**：`src/preprocessor.cpp:213,231,237,260,461,610,685,704,713`

### 条件编译栈

```cpp
struct CondState {
    bool parentActive;   // 外层是否活跃
    bool takenBranch;    // 本层是否已经有分支被取过
    bool active;         // 本层当前是否输出
};
```

| 笔记 | 说明 |
|---|---|
| "不是每个 `#if` 都进 vector，只要把活跃的 if 分支标记就行" | 栈只维护**嵌套层次**，不记录全部历史 |
| "这里就是代表了当前 if 分支" | `st.active = cond;` —— `active` 是"这一段要不要输出"的唯一判据 |

★ `takenBranch` 是 `#elif` 正确性的关键：`#if 0 ... #elif 1 ... #else` 里，
`#elif 1` 只有在"之前没取过任何分支"时才求值（[cpp.cond] 的短路语义）。

### 死分支

| 笔记 | 说明 |
|---|---|
| "死分支里的 `#define`/`#include` 等一律跳过" | 这正是 `#if 0 ... #endif` 能整段注释掉代码的原理 |
| "存在该定义" | `cond = m_macros.count(name) > 0` —— `#ifdef` 的判据是**宏表里有没有这个名字**，不关心值 |
| "就是将条件置为真" | `#ifdef` 求值后的形态：已定义替换成 `1`，否则 `0`，再交给常量表达式求值 |

### 宏展开

| 笔记 | 说明 |
|---|---|
| "宏展开" | 二阶段展开：① 实参各自完整展开 ② 代入宏体后再扫一遍（[cpp.replace]/9） |
| "这一部分是用于解析 `defined` 部分内容" | `defined(X)` 必须在宏展开**之前**求值，否则 `defined` 会被当普通标识符 |
| "这里会检测插入一条" | `#pragma once` 用文件规范路径做去重键 |

## 三、Parser —— 解析出的"只是符号"

**出处**：`src/parser.cpp:210,547,551,805,822,1215,1398,1410,1548,1557,1593`

> ★ **`parseType()` 解析出的类型只是符号，只是把类型的结构描述出来**

这句话是整个前端的纲领。`parseType()` 产出的是**结构**（`Pointer(Const(Int))`），
**不是**"这个类型占几个字节"—— 后者要等 Sema 的 `resolveType` 结合符号表才能算。

### 几个容易混的判定点

| 出处 | 笔记 | 说明 |
|---|---|---|
| `parser.cpp:1398` | "这里在头文件上默认声明了这两个变量" | `parseFunctionDecl(isVirtual, ownerClass)` 的两个默认参数 |
| `parser.cpp:1410` | "解析出返回类型" | 顺序：`[virtual]` → 返回类型 → 函数名 → 参数表 → `[override]` → 函数体 |
| `parser.cpp:1548` | "说明这里是 `MyObj value` 这样的类型" | 前瞻失败后**回退**到类型分支：`MyObj value;` 与 `foo();` 前两个 token 相同 |
| `parser.cpp:1557` | "可能是表达式，比如 `foo()` 这样的函数语句" | 这就是 [stmt.ambig] 的雏形：`T x;` 是声明，`f();` 是表达式语句 |
| `parser.cpp:1593` | "这里就是语句" | 拿到声明/表达式的裁决结果后，落到语句构造 |
| `parser.cpp:805` | "`expect` 会往前推进" | `expect()` = 检查 + 消费，失败即报错；`check()` 只看不动 |
| `parser.cpp:1215` | "左括号" | 类体起始的 `{` 用 `expect` 强制消费 |
| `parser.cpp:547/551` | "模板 / 触发方式为 class 或者 struct" | `parseTemplateDecl` 的第一个分叉 |

## 五、模板实例化 —— 我最初卡住的地方

**出处**：`src/semantic_analyzer.cpp:4184,4193,4235`

> ★ **"这里就是我一直想要的部分：对 template 进行实例化解析"**
> —— 落在 `getOrInstantiateClass` 的「深拷贝蓝图 + 结构化替换」那一段

这条链是理解模板机制的入口，三站依次是：

```text
resolveType(Box<int>)                        ← 只认名字
   └─ getOrInstantiateClass
        ├─ :4184  实例缓存 key = "Box<int>"   ← 同一个实例只算一次
        ├─ :4193  从 m_classTemplates 查主模板 ← "是哪个模板"在这
        ├─ selectClassTemplate               ← 三路择优（全特化/偏特化/主模板）
        └─ :4235  深拷贝蓝图 + 结构化替换     ← 真正"实例化"发生的地方
```

| 笔记 | 说明 |
|---|---|
| "这里是实例 cache" | 缓存键是「模板名 + 实参可读串」，`Box<4>` 与 `Box<int>` 天然不同键 |
| "从 class Template 里面去寻找" | `m_classTemplates` 是 `unordered_map<string, TemplateDeclPtr>`，O(1) |
| "这里就是我一直想要的部分" | 深拷贝 + 替换 —— 详见 `docs/learn/` 模板系列 |

**相关文档**：模板选择的完整链条见 `docs/learn/19`（类模板特化）、`docs/learn/20`（偏序裁决）；
替换引擎见 `docs/learn/27`（别名模板，其中"替换 ≠ 实例化"一节解释了这个函数最容易踩的坑）。
